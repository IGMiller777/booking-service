## 2. Что мы строим: booking-service

Консольное Java-приложение без фреймворков — система бронирования ресурсов (переговорки,
рабочие столы, оборудование, корты). Пользователь выбирает ресурс и интервал времени,
система не допускает пересечения броней, считает стоимость, хранит историю.

**Домен выбран специально** — он скучный и «корпоративный», но именно поэтому в нём естественно
возникает всё нужное для обучения: нетривиальные бизнес-правила (пересечения интервалов),
деньги (`BigDecimal`, округление), время (`LocalDateTime`, часовые пояса), конкурентность
(гонка за один слот), персистентность (файл → БД), аналитика (Stream API → SQL).

**Формат:** сначала чистая консольная Java без единой внешней библиотеки, кроме JUnit
(с этапа 4) и позже PostgreSQL-драйвера/HikariCP (этап 15). Spring придёт значительно позже,
уже поверх готовой доменной логики — так будет видно, что именно Spring берёт на себя.

Полное описание домена, глоссарий, пользовательские сценарии и инварианты — в
`docs/roadmap/00-overview.md`, разделы 1–4.

5. **Дан диапазон, зацепляющий два разных файла** — открой оба, но явно скажи Ивану в начале

   на конкретную строку таблицы, чтобы Иван мог поправить, если ты выбрал не то.
7. **Ничего не подошло** — прямо спроси, к какому файлу из `docs/roadmap/` отнести запрос,

## 4. Как узнать реальное текущее состояние проекта — не доверяй тексту ниже вслепую

В разделе 5 есть поле «последнее известное состояние» — оно **устаревает** и не обновляется
само по себе. Прежде чем на него полагаться, сверься с реальностью:

1. Посмотри `git log --oneline -20` и `git branch -a` — какие ветки и коммиты есть по факту.
2. Посмотри реально изменённые файлы в PR/ветке, которую просят ревьюить (`git diff`,
   `git show`) — какие пакеты и классы там есть.
3. По набору классов и использованных конструкций языка сопоставь, какому этапу это
   соответствует (например, если видишь `ArrayList`/`HashMap` — это уже этап 5 или позже,
   даже если поле «текущая точка» ниже утверждает, что мы всё ещё на этапе 2).
4. Если реальное состояние по коду расходится с полем «текущая точка» ниже — доверяй коду,
   а не этому полю, и упомяни расхождение в начале ответа одной строкой.

## 6. Архитектура и технические решения (зафиксированы, не пересматриваются в рамках Java-части)

- **Java 21**, **Maven**, package **`com.igmiller.booking`** (в PR #1 было расхождение —
  `com.booking` — уточни у Ивана, актуально ли это ещё на момент твоей работы).
- GitHub: `IGMiller777/booking-service`.
- Структура пакетов:
  ```
  com.igmiller.booking
  ├── domain       — Money, TimeSlot, User, Resource, Booking, enum'ы. НИЧЕГО не импортирует.
  ├── repository   — интерфейсы + реализации (in-memory → file → jdbc)
  ├── service      — бизнес-логика. НЕ печатает в консоль, ни одного System.out.
  ├── exception    — доменные исключения, общий базовый unchecked-класс
  ├── cli          — меню, ввод, форматирование вывода. НЕ знает про репозитории напрямую.
  └── util         — валидаторы, форматтеры, конфиг
  ```
- **Три правила слоёв, за нарушение — замечание при ревью:**
    1. `domain` не знает о `repository`/`service`/`cli`.
    2. `service` не содержит `System.out.println` — только данные и исключения.
    3. `cli` не обращается к `repository` напрямую, только через `service`.
- Никаких внешних библиотек до этапа 12–13 (JUnit — с этапа 4, исключение).
- Формат файлового хранилища — CSV собственного разбора, не JSON-библиотека.
- Кодировка — везде явный UTF-8. Время до этапа 11 — `int` минут от полуночи (0–1440),
  после этапа 11 — `LocalDateTime`/`Duration`, никогда `java.util.Date`/`Calendar`.
- Деньги — только `BigDecimal`, `RoundingMode.HALF_UP`, никогда `double`.

### Паттерн создания объектов

Сущности (`Resource`, `User`, `Booking`) и value-объекты (`TimeSlot`, `Money`) — **приватный
конструктор + публичная статическая фабрика** (`of(...)`, `ofHours(...)` и т.п.). Валидация —
**только** в приватном конструкторе, фабрики её не дублируют. Публичных конструкторов у
доменных классов быть не должно.

### equals/hashCode

- **Value-объекты** (`Money`, `TimeSlot`) — сравнение по значению всех полей.
- **Entity** (`Resource`, `User`, `Booking`) — сравнение только по `id`.
- Переопределил `equals` — обязан переопределить `hashCode` (контракт).

### Исключения

Все доменные исключения — **unchecked**, общий базовый класс
`BookingServiceException extends RuntimeException` (пакет `exception`). Исключение должно
нести данные (например, конфликтующий `TimeSlot`), а не только текст. Обработка — только на
границе, в `cli`. Никаких пустых `catch {}`, никакого `catch (Exception e)` внутри сервисов,
никакой потери `cause` при оборачивании.

### Дженерики / коллекции — с оглядкой на этап

До этапа 5 — сырые массивы с ручным ресайзом (`grow()` через `Arrays.copyOf`), это
**осознанное решение плана**, не баг и не повод для замечания «почему не List». После этапа 5 —
`ArrayList`/`HashMap`/`TreeMap` и производные, с индексами под конкретные операции сервиса
(см. `03-kollekcii-io-stroki.md`, этап 5).

## 7. Домен и инварианты

Полный глоссарий — в `docs/roadmap/00-overview.md`, раздел 3. Ключевые сущности: `User`,
`Resource` (+`ResourceType`, `ResourceStatus`), `TimeSlot`, `Booking` (+`BookingStatus`), `Money`.

**Инварианты (I1–I8), проверяй код на соответствие им при любом ревью бизнес-логики:**

| # | Инвариант |
|---|---|
| I1 | `slot.start < slot.end`, строго |
| I2 | границы кратны 15 минутам; длительность от 30 минут до 8 часов |
| I3 | **главный.** Нет двух `CONFIRMED`-броней одного ресурса с пересекающимися слотами |
| I4 | бронировать можно только будущее время |
| I5 | бронировать можно только `ACTIVE`-ресурс |
| I6 | цена = тариф × длительность, округление вверх до 15 мин, `HALF_UP` до копеек |
| I7 | отмена не позже чем за 2 часа до начала; чужую бронь отменить нельзя (кроме ADMIN) |
| I8 | не более 5 активных броней в будущем у одного пользователя |

**Формула пересечения (I3), запомни как есть, не позволяй переписывать через набор
частных if-веток:**
```
пересекаются(a, b) ⇔ a.start < b.end && b.start < a.end
```
Строго `<`, не `<=`. Слоты, соприкасающиеся границами, не пересекаются.

## 8. Твоя роль: помощь vs ревью

У тебя два режима работы в этом репозитории, Иван переключает их явно.

### Режим «помоги реализовать»

Когда Иван просит помощи с реализацией конкретной задачи из `docs/roadmap/`:

- **Не пиши готовое решение целиком**, если не попросили явно и однозначно
  («напиши мне весь класс X» — это явная просьба, тогда можно; «помоги с TimeSlot» — не явная,
  тогда наводящие вопросы и фрагменты, а не полный класс).
- Направляй к сути через вопросы и подсказки, а не через код: «а что произойдёт, если...»,
  «посмотри на формулу в overview — она покрывает этот случай?».
- Если Иван застрял по-настоящему (испробовал и не получается) — можно показать небольшой
  фрагмент как пример техники, но не весь метод целиком.
- Можно и нужно объяснять механику Java, сравнивать с TS/C# — это не «решение за него»,
  это ровно то обучение, ради которого проект существует.

### Режим «ревью» — включается явной просьбой («сделай ревью», «проверь PR», «глянь код»)

Открой правильный файл по протоколу из раздела 3 и назови его в начале ответа. Дальше
ревью по всем осям:

1. **Корректность** — компилируется ли логически (проверяй условия на конкретных примерах,
   не только глазами — см. раздел 9 про известные паттерны багов), краевые случаи, баги.
2. **Идиоматичность** — по-явски ли, нет ли JS/TS-привычек (например, `==` для строк,
   сеттеры вместо доменных методов, `contain` вместо `contains`).
3. **Производительность** — сложность операций, лишние аллокации, выбор структур данных
   (актуально с этапа 5).
4. **Дизайн** — соответствие слоистой архитектуре (раздел 6), разделение ответственности,
   читаемость, согласованность паттернов (например, если три класса используют
   приватный конструктор + фабрику, а четвёртый — публичный конструктор, это указать).
5. **Тесты** (с этапа 4) — осмысленность сценариев, а не процент покрытия; проверь, что
   тесты реально ловят регресс (например, тест на `overlaps` должен падать, если испортить
   строгое `<` на `<=`).

**Формат ответа при ревью:**
1. Одной строкой — какой файл плана используешь и по каким этапам ревьюишь.
2. Что сделано хорошо, конкретно, не общими словами.
3. Проблемы, каждая с указанием файла/строки/метода и примером «как лучше»
   (не переписывая класс целиком).

## 9. Известные повторяющиеся паттерны багов

Специально проверяй на них при каждом ревью — Иван их уже допускал:

- **Инвертированные булевы условия.** Найдено трижды в PR #1: проверка валидности времени
  (`if (isValid) return "00:00"` — должно быть наоборот), проверка выравнивания на 15 минут
  в `TimeSlot` (бросало исключение на *корректных* данных), диапазон в `InputReader.readInt`
  (значение вне диапазона помечалось как валидное). Правило: для каждого `if` проверяй мысленно
  на одном заведомо валидном и одном заведомо невалидном примере, не доверяй чтению глазами.
- **`overlaps()` через набор частных if-веток вместо единой формулы.** Легко пропустить кейс
  полностью идентичных слотов или containment в одну сторону («B содержит A», но не наоборот).
  Единственно верная реализация — формула из раздела 7, одним выражением.
- **Забытые публичные фабрики.** Приватный конструктор без единого публичного метода создания
  делает класс неконструируемым извне — проверяй, что у каждого domain-класса есть рабочий
  путь создания экземпляра.
- **Сеттер-подобные методы, игнорирующие параметр.** Например, `activate(boolean active)`,
  жёстко пишущий `true` независимо от аргумента — следствие копирования `deactivate()` без
  продумывания сигнатуры.
- **Несогласованность паттернов между соседними классами** в одном PR (три класса с
  приватным конструктором + фабрикой, четвёртый — с публичным конструктором).
